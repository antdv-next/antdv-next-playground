# Antdv Next Playground

[中文](./README.zh-CN.md)

Online playground for [antdv-next](https://github.com/antdv-next/antdv-next), powered by [@vue/repl](https://github.com/vuejs/repl).

## Usage

Go to [antdv-next-playground](https://play.antdv-next.com) to have a try!

## Development

```bash
pnpm install
pnpm dev
```

## Notes

### Vue >= 3.5.0

The Vue version selector is restricted to **>= 3.5.0**.

Reason: The antdv-next dependency `@v-c/color-picker` uses `onWatcherCleanup` (a Vue 3.5+ API), which is bundled into `antdv-next/dist/antd.esm.js`. Selecting a Vue version below 3.5 will cause the preview to error:

```
Uncaught SyntaxError: The requested module 'vue' does not provide an export named 'onWatcherCleanup'
```

> antdv-next itself does not directly use this API — it is introduced by an indirect dependency. If the upstream removes this dependency, the version restriction can be relaxed.

### URL Parameters (Pro / X)

Pro and X are **off by default** — their dependencies are not imported into the sandbox. Enable them via the Settings dialog, or via URL parameters so docs/demo pages can deep-link:

- `?pro=1` — enable Pro (`@antdv-next/pro`)
- `?x=1` — enable X (`@antdv-next/x`)
- `?pro=1&x=1` — enable both
- `0` / `false` / `no` / `off` explicitly disable (e.g. `?x=0`)

The parameters are preserved across reloads. Once a feature is toggled in the UI, the choice is saved into the shareable URL and takes precedence over the parameter.

### Antdv Next >= 1.0.4

The antdv-next version selector is restricted to **>= 1.0.4**.

Reason: npm packages for versions 1.0.0 ~ 1.0.3 do not include `dist/antd.esm.js` (different early build structure, using `dist/index.js` instead). The Playground relies on this ESM bundle to run in the browser, so older versions will result in a 404.

### Import Map Architecture

The sandbox resolves the dependency graph through a layered import map (`genImportMap` in `src/utils/dependency.ts`), so that internal import changes inside dependencies (e.g. `@v-c/picker@1.5.0` switching dayjs plugin imports to a `.js` suffix) no longer break the preview:

- **Tier 1 — raw dist (CDN-switchable)**: `vue`, `antdv-next` core entries, `@antdv-next/icons` (single-file bundle on purpose — an exports-map entry would request 852 icon files). These hold the singletons (vue runtime, config-provider/theme context) that user code, Pro and X must share.
- **Tier 2 — esm.sh + `?external=`**: `@v-c/*`, `@antdv-next/cssinjs`, `@vueuse/*`. Each package gets exact keys for its root and public/deep subpaths; the `external` list (all shared singletons + all Tier 2 roots + all leaf packages) keeps those imports bare so the import map stays the single source of module identity. Tier 2 can **not** use trailing-slash prefix keys: prefix mapping is a plain string substitution and cannot append `?external=`, and a build without `external` bundles its own copy of vue. Two caveats learned the hard way: a package is always removed from its own `external` list (otherwise esm.sh rewrites its internal relative imports to self-referencing bare specifiers that no import-map key covers), and extensionless subpath keys get a `.js` alias against spelling drift.
- **Tier 3 — esm.sh prefix (leaf packages)**: stateless leaves (`es-toolkit`, `stylis`, etc.) get a root key plus a trailing-slash prefix key, so any subpath spelling resolves at request time. Exceptions: `dayjs` core and the CJS packages `@ant-design/colors` / `@ant-design/fast-color` use the CDN-switchable `+esm` transform (esm.sh's CJS named-export detection drops exports for them); `dayjs/plugin/` and `dayjs/locale/` use esm.sh prefixes (plugin builds are self-contained — they receive the dayjs instance via `extend`, so no singleton concern).

Runtime version following: when you switch the antdv-next version, `resolveAntdvDeps` re-resolves its direct dependencies and overrides the snapshot versions from `src/utils/esm-packages.ts` (generated by `scripts/gen-static-imports.mjs`, checked in CI via `pnpm verify:imports`).

Escape hatch: if esm.sh is unreachable, `?resolver=legacy` (also in the Settings dialog) falls back to the frozen full-enumeration map (`src/utils/static-imports.ts` + jsDelivr raw/`+esm` artifacts), matching the pre-refactor behavior. The resolver setting persists in localStorage; the CDN setting is orthogonal and still controls Tier 1, `+esm` packages, CSS URLs and X data files.

Self-check for instance duplication: filter `esm.sh` in DevTools Network — `vue`/`runtime-dom` should appear exactly once, and every `@v-c/*` URL should carry the full `external` list. A narrowed `?external=vue` URL means a Tier 2 root leaked out of the external set (regenerate `esm-packages.ts`).
